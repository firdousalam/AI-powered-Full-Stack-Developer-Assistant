# 📌 Introduction

In the previous milestone, we explored the fundamentals of the **Model Context Protocol (MCP)** and understood how it enables AI applications to communicate with external tools using a standardized protocol.

Until now, our **AI-powered Full Stack Developer Assistant (Zeba AI)** has relied primarily on:

* User prompts
* Browser Context collected from the active webpage
* Large Language Models (Ollama/OpenAI)

While this architecture is powerful, it has one significant limitation:

> **The AI has no direct access to the developer's local project.**

For example, if a user asks:

* Explain my `package.json`
* Review my `Dockerfile`
* Read my `README.md`
* Analyze my Kubernetes deployment
* Find all TODO comments

The language model cannot answer accurately because it has no way to access those files.

This is where **Model Context Protocol (MCP)** becomes an essential part of our architecture.

MCP provides a standardized bridge between the AI model and external developer tools, allowing the AI assistant to securely access project resources without embedding tool-specific logic into the language model itself.

In this milestone, we will begin integrating MCP into our existing backend architecture.

Our objective is **not** to build a fully autonomous coding assistant yet. Instead, we will establish a solid foundation that future milestones can build upon.

## Request Flow

The current request lifecycle looks like this:

1. The user opens the Chrome Extension.
2. The extension collects Browser Context from the active webpage.
3. The Browser Context and user prompt are sent to the Express Backend.
4. The AI Controller validates the request.
5. The AI Service constructs the final prompt.
6. The prompt is sent to Ollama (or another supported LLM).
7. The generated response is streamed back to the extension.

This architecture works well for browser-based assistance, but it has no awareness of the developer's local workspace.

---

# 🚨 Why Do We Need MCP?

Imagine the following scenario.

A developer asks:

> **Explain my Dockerfile.**

Our backend sends the prompt to Ollama.

Unfortunately, Ollama has never seen the user's Dockerfile.

The AI can only guess what the Dockerfile might contain.

The same limitation exists for:

* package.json
* tsconfig.json
* README.md
* Kubernetes YAML files
* Source code
* Configuration files
* Environment variables

Without access to the project, every answer is based on assumptions rather than facts.

---

Without MCP:

```text
User

        │
```

The language model cannot:

* Read local files
* Search folders

* Inspect Git repositories
* Analyze Docker images
* Query Kubernetes clusters

As a result, the AI is forced to generate generic responses.

## The Solution

Instead of guessing, the AI retrieves real information before generating a response.


The AI now works with actual project data instead of assumptions.

Our backend will evolve from a simple AI proxy into an orchestration layer that coordinates communication between the user, the language model, and external developer tools.

```text
                           |
```

In this architecture:

* The Chrome Extension remains lightweight.
* The backend becomes the orchestration layer.
* The AI Service decides when external tools are required.
* The MCP Client communicates with MCP Servers.
* MCP Servers perform real-world operations.
* The LLM focuses on reasoning and response generation.

This separation of responsibilities keeps the system modular, scalable, and maintainable.

# 🔄 How MCP Fits into Our Existing Backend

One of the most important design decisions in this project is **where the MCP Client should live**.

A common mistake is to allow the Chrome Extension to communicate directly with MCP Servers.

We will **not** do that.

Instead, the backend remains the single entry point for all AI requests.

The updated request flow becomes:

```text
Chrome Extension

        │

        ▼

Express API

        │

        ▼

AI Controller

        │

        ▼

AI Service

        │

        ├──────────────► Ollama / OpenAI
        │
        │
        ▼

MCP Client

        │

        ▼

Filesystem MCP Server

        │

        ▼

Local Project Files
```

This architecture provides several advantages:

* **Security:** The browser never receives direct access to the user's filesystem.
* **Centralized Logic:** All AI workflows remain inside the backend.
* **Scalability:** New MCP Servers can be added without changing the Chrome Extension.
* **Maintainability:** Business logic, AI orchestration, and tool execution remain clearly separated.
* **Reusability:** The same MCP Client can be used by web applications, VS Code extensions, mobile clients, or desktop applications.

In future milestones, this design will allow us to integrate GitHub, Docker, Kubernetes, databases, and cloud services simply by registering additional MCP Servers, while keeping the rest of the application unchanged.

# 📌 Goal

In the previous milestone, we learned the fundamentals of the **Model Context Protocol (MCP)** and how it enables AI applications to communicate with external tools.

As our AI-powered Full Stack Developer Assistant grows, it will eventually communicate with multiple MCP Servers such as:

* Filesystem
* GitHub
* Docker
* Kubernetes
* PostgreSQL
* MongoDB
* Redis
* AWS
* Azure

Managing these servers directly inside the AI Service would quickly become difficult to maintain.

To solve this problem, we introduce an **MCP Gateway**.

The MCP Gateway acts as a centralized communication layer between the AI Service and one or more MCP Servers.

Instead of every service creating its own MCP connections, the entire application communicates through the Gateway.

This design keeps the backend modular, scalable, and easier to extend in future milestones.

# 🏗 Current Backend Architecture

Our backend currently looks like this:


---

# ❌ Problems with Direct Connections

As the number of MCP Servers grows, the AI Service becomes responsible for:

* Creating server connections
* Managing reconnections
* Health checking
* Loading configuration
* Selecting the correct server
* Error handling
* Authentication

This violates the **Single Responsibility Principle (SRP)**.

The AI Service should focus only on AI orchestration—not infrastructure management.

---

# ✅ Introducing the MCP Gateway

Instead of allowing the AI Service to communicate directly with every MCP Server, we introduce a dedicated Gateway.

```text
Chrome Extension
        │
        ▼
Express Backend
        │
        ▼
AI Controller
        │
        ▼
AI Service
        │
        ▼
MCP Gateway
        │
 ┌──────┼──────────┬──────────┬─────────┐
 ▼      ▼          ▼          ▼         ▼

Filesystem GitHub Docker Kubernetes PostgreSQL
```

The AI Service now communicates with only one component:

**The MCP Gateway.**

The Gateway handles everything related to MCP communication.

---

# 🏛 What is the Gateway Pattern?

The **Gateway Pattern** is a software architecture pattern that provides a single entry point for accessing multiple external systems.

Instead of every module communicating with external services individually, all communication flows through one gateway.

Benefits include:

* Centralized communication
* Simplified architecture
* Easier maintenance
* Better scalability
* Improved testing
* Reduced code duplication

---

# Why Use an MCP Gateway?

Imagine that six months from now our assistant supports:

* Filesystem
* GitHub
* Docker
* Kubernetes
* PostgreSQL
* MongoDB
* Redis
* AWS

Without a Gateway:

```text
AI Service

│

├── Filesystem Client

├── GitHub Client

├── Docker Client

├── Kubernetes Client

├── PostgreSQL Client

├── MongoDB Client

├── Redis Client

└── AWS Client
```

The AI Service becomes tightly coupled to every integration.

With a Gateway:

```text
AI Service

        │

        ▼

MCP Gateway

        │

 ┌──────┼──────────┬────────────┐

 ▼      ▼          ▼            ▼

Filesystem GitHub Docker Kubernetes
```

Adding a new MCP Server requires changes only in the Gateway.

---

# MCP Gateway Responsibilities

The Gateway is responsible for:

* Managing server connections
* Loading configuration
* Registering servers
* Selecting servers
* Monitoring health
* Forwarding requests
* Reconnecting disconnected servers
* Logging communication
* Returning responses

It is **not** responsible for AI reasoning.

# gateway.ts

The Gateway acts as the public API for all MCP communication.

Responsibilities include:

* Connect to servers
* Execute tools
* Find servers
* Monitor connections
* Return responses

Every AI request involving MCP will pass through this file.

---

# registry.ts

The Registry maintains a list of available MCP Servers.

Example:

```text
Filesystem

GitHub

Docker

Kubernetes

PostgreSQL
```

The Registry answers questions such as:

* Which servers are available?
* Is a server connected?
* Which transport is being used?
* Which server supports a requested tool?

---

# types.ts

This file contains shared interfaces and type definitions.

Examples include:

* MCP Server
* Gateway Configuration
* Tool Definition
* Health Status
* Server Metadata

Centralizing types improves maintainability and type safety.

---

# config.ts

All Gateway configuration belongs here.

Examples:

* Server names
* Transport type
* Connection timeout
* Retry policy
* Logging configuration
* Health check interval

Keeping configuration separate avoids hard-coded values.

---

# Dynamic Registration

One of the biggest advantages of the Gateway is that servers can be registered dynamically.

Instead of writing:

```text
gateway.addFilesystem()

gateway.addGitHub()

gateway.addDocker()
```

we maintain a registry.

```text
Gateway

↓

Registry

↓

Registered Servers
```

Adding another server becomes straightforward.

```text
Register Server

↓

Gateway discovers it automatically

↓

Available to AI
```

This architecture scales much better.

---

# Server Registry

The Registry maintains metadata about every connected server.

Example information:

* Server Name
* Version
* Status
* Transport
* Supported Tools
* Connection State

Example table:

| Server     | Status       | Transport | Tools                     |
| ---------- | ------------ | --------- | ------------------------- |
| Filesystem | Connected    | stdio     | Read File, List Directory |
| GitHub     | Disconnected | HTTP      | Repository APIs           |
| Docker     | Connected    | stdio     | Build, Run, Stop          |
| Kubernetes | Connected    | stdio     | Deploy, Scale             |

The AI Service never needs to know these implementation details.

---

# Health Checking

Before using a server, the Gateway should verify that it is healthy.

Health monitoring helps detect:

* Crashed servers
* Lost connections
* Authentication failures
* Timeouts
* Transport failures

Typical health states include:

```text
Healthy

Degraded

Disconnected

Unavailable
```

The Gateway can periodically poll servers or use heartbeat messages depending on the transport.

---

# Connection Lifecycle

Every MCP Server follows a lifecycle.

```text
Created

↓

Connecting

↓

Connected

↓

Healthy

↓

Disconnected

↓

Reconnect

↓

Connected
```

The Gateway is responsible for managing these transitions and recovering from failures whenever possible.

---

# Configuration Management

Typical configuration options include:

* Server name

* Transport
* Timeout
* Retry attempts
* Startup arguments
* Environment variables

Centralizing configuration allows different environments (development, testing, production) to use different server settings without changing application code.
